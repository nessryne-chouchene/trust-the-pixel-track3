TSYP14 — Ground Truth Under Attack

Satellite Image Security Assessment

This project checks whether a satellite image can be trusted before any AI model looks at it. It answers three questions: Is this a real, undamaged image file? Did it really come from a trusted satellite operator, unchanged? And have we already seen it?

A · Project overview

What does this project do?

Earth-observation images are used to make real decisions: crop insurance payouts, water management, disaster response. If an attacker can slip in a fake, edited or recycled image, people may act on something that never happened.

The idea in one paragraph

A satellite operator does not just send a picture. It also sends a short manifest (a delivery note describing the picture: when and where it was taken, by which sensor, and the picture's unique digital fingerprint) and a digital signature on that manifest. Our program, the receiver, checks the file, the signature, the fingerprint, the description and its own memory of past images, then gives one verdict: PASSED, REVIEW or FAILED.

Everyday comparison: think of a registered parcel. The box (the image) comes with a delivery note sealed by the sender (the signed manifest). You check the seal is genuine, that the note really describes what is in the box, that the details make sense, and that you were not already sent this exact parcel.

What arrives with each image

scene_001.png

The image itself (PNG, JPEG or TIFF). Not signed directly.

scene_001.manifest.json

The description: fingerprint (SHA-256), time, sensor, latitude/longitude, key name, signing time, file name.

scene_001.manifest.sig

The sender's Ed25519 signature on the manifest, as one line of base64 text.

Important: checking origin is not the same as spotting fake pixels

This project proves where a file came from and that it was not changed on the way. It does not look at the picture to decide whether it was edited. If a trusted operator signs an image that was already doctored, it will pass. Detecting visual manipulation is the job of the AI stages shown above, which are future work.

B · How the system works

The security checks, step by step

The checks always run in the same order. Each problem found is recorded as a short reason code (for example HASH_MISMATCH) so a person can see exactly why an image was not accepted. All limits come from the configuration file test_data/policy.json.

Step 1

File validation

Before trusting anything, the program makes sure the file really is a normal, safe image.

  • The file exists and is not empty.
  • The extension is allowed: .png, .jpg/.jpeg, .tif/.tiff.
  • The size is at most 100 MB.
  • The first bytes of the file (its “magic bytes”, like a label inside the box) match the extension.
  • The image library (Pillow) recognises the same format.
  • Width × height is at most 40 million pixels — read from the header before decoding, so a tiny file that claims to be gigantic (a “decompression bomb”) cannot exhaust memory.
  • The whole image decodes without errors (catches truncated or corrupted files).

⛔ If any of these fail, the program stops immediately with FAILED. The later checks are reported as “not evaluated” (null).

ExampleA text document renamed scene_012.png does not start with the PNG magic bytes → FAILED with FORMAT_MAGIC.
Reason codes

FORMAT_MISSING file not found (a code added by this project; not in the guide) · FORMAT_EXTENSION · FORMAT_SIZE (also used for empty files) · FORMAT_MAGIC · FORMAT_DECODE · FORMAT_DIMENSIONS.

The file is read into memory once; the very same bytes are decoded and fingerprinted, so the file cannot be swapped between two checks.

Step 2

Digital signature verification

Each operator owns a secret private key and uses it to sign the manifest. The receiver only stores the matching public keys in trusted_keys.json. A public key can check a signature but can never create one — like a wax seal that only the owner's ring can make, but that anyone can compare with a reference print.

  • The manifest is readable and contains every required field.
  • A .sig signature file exists.
  • The key named in the manifest (key_id) is in the trust store.
  • The key is active, not revoked — checked before any cryptography.
  • The signing time (signed_at) lies inside the key's validity period.
  • The Ed25519 signature is valid for the exact manifest content.

These run in order and stop at the first problem. The result is FAILED if any fails.

ExampleSomeone edits the latitude in a manifest after it was signed → the signature no longer matches → SIG_INVALID. A signature made with a key the receiver revoked → KEY_REVOKED, even though the maths is correct.
Technical detail: what exactly is signed

The signed bytes are a fixed prefix line followed by the manifest written as compact JSON with sorted keys, in UTF-8:

b"TSYP14-IMG-MANIFEST-v1\n" + json.dumps(manifest, sort_keys=True,
    separators=(",", ":"), ensure_ascii=False).encode("utf-8")

Codes: MANIFEST_INVALID · SIG_MISSING · KEY_UNKNOWN · KEY_REVOKED · KEY_NOT_VALID · SIG_INVALID. The program never needs, stores or reveals a private key.

Step 3

Image integrity (SHA-256)

The signature protects the manifest, not the image. The link between them is the image's fingerprint: a SHA-256 hash, a 64-character code computed from every byte of the file. Change a single pixel and the fingerprint changes completely.

  • The program computes the fingerprint of the image it actually received.
  • It compares it with the fingerprint written in the manifest — only after the signature was verified, so the manifest's value can be trusted.
ExampleA red rectangle is drawn on an image after it was signed. The manifest and signature are untouched, so the signature check passes — but the fingerprints differ → FAILED with HASH_MISMATCH.
Why is this needed if the signature is valid?

Because an attacker could keep a genuine manifest and signature and simply replace the picture next to them. Only the fingerprint comparison notices that swap. In the result, the flag signature_valid covers both step 2 and step 3.

Step 4

Metadata validation

A genuinely signed image can still carry suspicious details. These checks always run (even if the signature failed) and every problem found is listed.

  • Time, sensor, latitude and longitude are all present.
  • Latitude is a number between −90 and 90; longitude between −180 and 180.
  • The sensor is one the signing key is allowed to speak for (a key for satellite ALPHA cannot vouch for satellite BRAVO).
  • The time is written as YYYY-MM-DDTHH:MM:SSZ.
  • The time is not more than 300 seconds in the future (small clock drift is tolerated).
  • The observation is at most 72 hours old.
  • The file name in the manifest equals the name of the received file.

Ages are measured against a fixed reference time (2026-10-13T12:00:00Z in reference_time.txt), not the computer's clock, so results never change as the files get older.

ExampleA signed manifest says latitude 123.4 and sensor SAT-UNKNOWN → REVIEW with META_LATITUDE, META_SENSOR.
Reason codes

META_MISSING_FIELD · META_LATITUDE · META_LONGITUDE · META_SENSOR · META_TIME_INVALID · META_TIME_FUTURE · META_TIME_STALE · META_FILENAME (always in this order).

If the signing key is unknown, the sensor is accepted when it belongs to any trusted key.

Step 5

Replay attack detection

A replay is re-sending something that was already accepted, for example an old image presented as today's. The receiver keeps a memory of accepted images, the ledger (ledger.json), listing each image's ID and fingerprint.

  • The image ID must not already be in the ledger (REPLAY_ID).
  • The image's fingerprint must not already be in the ledger, which catches an attacker who only renames the ID (REPLAY_CONTENT).
ExampleAn image with a fresh ID but exactly the bytes of an image accepted yesterday → FAILED with REPLAY_CONTENT.
When is the ledger updated?

Assessing an image never changes the ledger. An image is added only when it PASSED and you ask for it (the --record option, or the record_accepted() function). Recording rejected images would let an attacker “burn” legitimate IDs by sending garbage. The file is rewritten safely (temporary file, then replace), so a crash cannot leave it half-written.

Step 6

Final security decision

The program combines all results into one verdict using three simple questions:

  1. Did the file check, signature or fingerprint fail, or was a replay found? → FAILED
  2. Otherwise, did a metadata check fail? → REVIEW (set by metadata_failure_action in the policy; it can also be set to FAILED)
  3. Otherwise → PASSED

The answer also lists all reason codes, in check order, plus human-readable reasons and an evidence trail (fingerprint, key, policy version, every check with pass/fail).

The three possible results

PASSED

Every required check succeeded.

The image may continue to the next stage of the pipeline.

REVIEW

The image is authentic and unchanged, but its description looks wrong (e.g. impossible coordinates, too old).

A trusted sender can make mistakes — a human should take a look.

FAILED

A mandatory check failed: bad file, bad or missing signature, untrusted or revoked key, changed image, or a replay.

The image is rejected.

C · Project files

What each file is for

Three Python programs do the work. They are kept separate on purpose: the checker never sees the expected answers, and the test-data generator does not reuse the checker's code, so a mistake in one cannot be silently copied into the other.

How the pieces work together

  1. generate_test_dataset.pycreates the test images and answers
    ➜
  2. test_data/images, manifests, signatures, expected.json
    ➜
  3. run_security_cases.pyruns each case, compares with expected.json
    ➜
  4. security_assessment.pycalled for every case: the actual checker
    ➜
  5. test_results/results.json + results.csv
    ➜
File or folderRole
security_assessment.pyThe checker. Contains assess(), which runs all the checks on one image and returns the verdict, plus helper functions to load the configuration files and to add a PASSED image to the ledger. It can also be used from the command line on a single image. It only uses public keys and never reads test answers.
generate_test_dataset.pyThe test-data factory. Draws small synthetic “satellite-like” pictures (fields, a road, a river), writes manifests, signs them with throw-away test keys and records the expected answer for each case. The test keys are derived from public labels, are never saved to disk, and must never be used for anything real. Running it twice gives identical files.
run_security_cases.pyThe examiner. Runs the checker on every test case, compares its answer field by field with expected.json, runs 5 extra safety checks, prints PASS/FAIL with explanations, and writes the reports.
tools/mutation_check.pyOptional quality check of the tests themselves. Makes 17 temporary copies of the checker, each with one deliberate bug (for example ignoring revoked keys), and confirms the tests catch every one. Your real files are never modified.
requirements.txtThe two Python libraries needed: cryptography (Ed25519 signatures) and Pillow (reading images).
README.mdThe technical reference: exact interface, every check, and the documented design choices where the official guide was not specific.
test_data/Generated test inputs. Shared files: trusted_keys.json (public keys), policy.json (limits and rules), ledger.json (already-accepted images), reference_time.txt (the fixed “now”). Sub-folders scenes/ (the 13 scenarios of the official guide) and edge_cases/ (35 extra cases). Each case folder holds the image, manifest, signature, case.json (which files to use) and expected.json (the answer key). CASES.md lists them all.
test_results/The reports written by the test runner: results.json (full detail) and results.csv (opens in Excel or LibreOffice).
web/This guide page: index.html, style.css and script.js. Open web/index.html in any browser.
.venv312/ (repository root)Your private Python environment, created during installation. Not part of the source code; you can delete and recreate it.

D · Install and run

How to install and run the project

You need Python 3 (the project uses Python 3.12 and the .venv312 environment at the repository root; the commands below run from src/security; this module was first tested with Python 3.14.5). No internet is needed after the two libraries are installed. Type each command in a terminal and press Enter. Copy buttons are provided.

Windows (PowerShell)

  1. Open PowerShell in the project folder

    Easiest way: open the tsyp14_security_assessment folder in File Explorer, click the address bar, type powershell and press Enter. Or open PowerShell and move into the folder (replace the path with where you saved it):

    cd "C:\path\to\tsyp14_security_assessment"

  2. Check that Python is installed

    py --version

    If this prints a version such as Python 3.14.5, continue. If py is not found, try python --version, or install Python from python.org and tick “Add python.exe to PATH”.

  3. Create a virtual environment (once)

    A virtual environment is a private folder (.venv) holding this project's libraries, so they do not interfere with anything else.

    py -3.12 -m venv .venv312

    Optional — activate it so you can type python instead of the full path. The commands below use the full path, so they work whether or not you activate.

    .\.venv312\Scripts\Activate.ps1

    If PowerShell says running scripts is disabled, allow it for this window only, then activate again:

    Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

  4. Install the dependencies (once)

    python -m pip install -r ..\..\requirements.txt

  5. Generate the synthetic test dataset

    python generate_test_dataset.py

    Expected output:

    Wrote 48 cases (13 guide scenes, 35 edge cases) to test_data/

    This rebuilds test_data/ from scratch (identical every time). It refuses to touch a test_data folder it did not create.

  6. Run the automated tests

    python run_security_cases.py

    The last lines should look like this (see Test results to read them):

    Summary: 53/53 passed, 0 failed (100.0%)
  scenes      13/13
  edge_cases  35/35
  invariants  5/5
Reports: test_results\results.json, test_results\results.csv

  7. Open the reports

    The spreadsheet version opens in Excel or LibreOffice; the JSON version opens in Notepad:

    start test_results\results.csv
    notepad test_results\results.json

Optional extras

Check a single image from the command line
python security_assessment.py --image test_data\scenes\03_image_tampered\scene_003.png --manifest test_data\scenes\03_image_tampered\scene_003.manifest.json

It prints the full result. The signature file defaults to the manifest name ending in .sig (--sig to choose another) and the configuration folder defaults to test_data (--config-dir). The program's exit code is 0 for PASSED, 2 for REVIEW, 3 for FAILED and 1 for a configuration error.

Caution: the --record option adds a PASSED image to ledger.json in the configuration folder. Doing that on test_data changes the expected test outcomes; run generate_test_dataset.py again to restore it.

Check that the tests really catch bugs (mutation check, about 1–2 minutes)
python tools\mutation_check.py

It should end with 17/17 mutants killed; survivors: none.

Run the tests against the official organiser data

If you have the official sample_input folder from the challenge, put it next to the project folder and run:

python run_security_cases.py --data-dir ..\sample_input --results-dir test_results\official

This has not been done yet: the official folder was not available when this project was built.

E · Understanding the results

How to read the test output

Each test case is an image scenario built to provoke one specific behaviour. The test runner checks that the program gives exactly the answer the official guide requires.

Two different questions — don't mix them up
  • Security decision (PASSED REVIEW FAILED): the program's verdict about the image.
  • Test outcome (PASS / FAIL): whether the program gave the right verdict.

A tampered image should be rejected. So when the program answers FAILED for it, the test is a PASS. The test would FAIL if the tampered image were accepted.

Anatomy of one line of output

[PASS]test outcome 03_image_tamperedtest case name FAILEDsecurity decision HASH_MISMATCHreason codes (“-” = none)

When a test does not match, the runner prints one explanation per wrong field. This is real output from a deliberately broken copy of the checker that ignores revoked keys:

[FAIL] 07_revoked_key                       PASSED  -
         -> signature_valid: expected false, got true
         -> security_status: expected "FAILED", got "PASSED"
         -> reason_codes: expected ["KEY_REVOKED"], got []

A test passes only if all of these match: the image ID, the four check flags, the final status, and the reason codes in the same order. The runner exits with code 0 if everything passed, 1 if anything failed, and 2 if the test data is missing.

The 35 extra edge cases and 5 safety checks — what they cover

All 35 edge cases and all 5 safety checks passed in the recorded run. They cover:

  • Broken or dangerous files: empty file, truncated PNG, .bmp file, PNG label followed by garbage, oversized file, a real 7000×6000 image (42 million pixels), a tiny file claiming 100000×100000 pixels, a JPEG renamed to .png, a missing image.
  • Manifest and signature problems: broken JSON, missing field, wrong version, duplicated field, missing manifest, signature that is not base64, too-short signature, expired key, not-yet-valid key, unreadable signing time.
  • Metadata problems: missing timestamp, longitude 200.5, latitude written as text, time 1 hour in the future, time 4 minutes ahead (tolerated → PASSED), badly written time, wrong file name, sensor belonging to another operator, four problems at once (checks the order of codes).
  • Combinations: unknown key and unknown sensor, tampered manifest with a bad latitude (FAILED wins over REVIEW), replay by both ID and content, a policy that turns metadata problems into FAILED, a clean .jpeg, and two manifests containing accented and Arabic text.
  • Safety checks: the checker never opens the answer files; it never changes the ledger; the ledger accepts only PASSED images (and a recorded image is then caught as a replay); identical inputs give identical results; a trust store containing a private key is refused.

The full list with expected flags and codes is in test_data/CASES.md.

F · Limitations and future work

What this project does not do (yet)

Current limitations

  • No visual manipulation detection. An image edited before a trusted operator signed it, or signed with a stolen key, will pass. The checks prove origin and integrity, not that the picture shows reality.
  • Synthetic test data only. The test images are simple generated 256×256 pictures. They prove the checking logic follows the specification; they say nothing about performance on real satellite imagery or sophisticated attacks.
  • Not yet tested on the official organiser data. The official sample_input folder was not available. The test runner can read it as-is once you have it.
  • Demo keys. The test keys are derived from public labels so the data is reproducible — anyone can recompute them. Real keys must be random and kept secret (ideally in a hardware security module).
  • No bit-depth or geographic-reference checks. TIFF files are checked as images, but GeoTIFF georeferencing and the “bit depth = 8” idea from the architecture diagram are not checked (the guide defines no reason code for them).
  • One writer at a time for the ledger. Ledger updates are crash-safe, but two programs recording images at the same moment are not coordinated.
  • Tested on Windows with Python 3.14.5 only.

Future improvements

  • AI forensics stages from the architecture: preprocessing, EfficientNet feature extractor, localization head (suspicious-region mask) and classification head (manipulation probability).
  • Combined report merging the security evidence with the AI results.
  • Run against the official sample data and real satellite imagery.
  • Optional extra checks such as bit depth and GeoTIFF coordinates matching the manifest.
  • Production key management: random keys, secure storage, key rotation.
  • Ledger locking or a small database if several receivers run in parallel.

Glossary

Technical terms in plain English

Click a term to open its explanation.

Hash / SHA-256 / fingerprint

A fixed-length code (64 hexadecimal characters for SHA-256) computed from a file's bytes. Identical files always give the same hash; changing even one byte gives a completely different one. It is practically impossible to make two different files with the same hash.

Digital signature

A small piece of data made with a secret key that proves who approved a message and that the message has not changed since. Anyone with the matching public key can check it; nobody without the secret key can make it.

Ed25519

A modern, widely used digital signature method. Its signatures are 64 bytes long and its public keys 32 bytes. Verification answers only “valid” or “invalid”.

Private key / public key

A matched pair. The private key is kept secret by the sender and used to sign. The public key is shared and used by anyone to verify. This project's checker only ever holds public keys.

Manifest

The signed “delivery note” sent with each image (.manifest.json): the image's fingerprint, size, file name, time, sensor, position, the name of the signing key, a unique value (nonce) and the signing time.

Base64

A way to write binary data using only letters, digits, +, / and =, so it can be stored in a text file. The .sig file holds the signature in this form; the checker decodes it before verifying.

Trust store

trusted_keys.json: the list of public keys the receiver trusts, each with its status (active or revoked), the sensors it may speak for, and its validity period.

Revoked key

A key that was trusted but is no longer (for example because it may have leaked). Signatures made with it are rejected even if they are mathematically correct.

Magic bytes

The first few bytes of a file that identify its real type. A PNG always starts with 89 50 4E 47 0D 0A 1A 0A, a JPEG with FF D8 FF, a TIFF with II* or MM*. Renaming a file does not change them.

Decompression bomb

A small file that claims to contain an enormous image. Decoding it could fill the computer's memory. The checker reads the claimed size from the header first and refuses images above 40 million pixels.

Replay attack

Re-sending a message or image that was genuinely accepted before, for example to make old imagery look current. Detected here by remembering accepted IDs and fingerprints.

Ledger

ledger.json: the receiver's memory of accepted images (ID, fingerprint, acceptance time). Only PASSED images may be added.

Policy

policy.json: the configurable rules — allowed formats, maximum file size (100 MB) and pixels (40 million), maximum age (72 h), clock tolerance (300 s), and what to do when only metadata fails (REVIEW).

Reference time

A fixed “now” (reference_time.txt) used for all time checks, so test results are the same today and next year.

Reason code

A short label such as HASH_MISMATCH naming one failed check. The list of codes explains a decision; it is empty for PASSED.

Synthetic dataset

Test data produced by a program rather than collected from the real world. Here: generated pictures plus carefully constructed manifests and signatures, each designed to trigger one behaviour.
